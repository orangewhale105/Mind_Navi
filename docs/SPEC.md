## 1. ソフトの目的・方法論・想定ユーザー・販売構想

### 1.1 目的
- マインドマップ形式で目標・タスクを整理するソフト（名称 Mind_Navi）。Python で開発。最初はミニマムに作り、使いながら拡張する方針。
- 「夢」などの名称はやめ、標準的な目標・タスク整理ツールとして開発する（旧称の別名として「DreamMap」がメモリーにある）。
- 思考整理・スケジューリング・買い物・メモを統合した日常管理ソフトにしたい。
- 個人利用では Google ドライブにデータを置き、スマホと PC の両方から使う。複数の PC（自宅・学校など）で同じデータを使う。

### 1.2 方法論
- 核：マインドマップで夢（目標）を列挙・構造化 → タスク化 → スケジューリングし、スケジュールから「夢のどこに当たるか」をすぐ見られるようにする（「三人のレンガ職人」の例え）。
- 流れ：思考整理 → 分析 → スケジューリング → タスク → ガントチャート。
- マップ上で何がタスクか・タスク間の前後関係を明示し、ガントチャートと1日の時間割へ往還させたい。
- マインドマップの拡散しすぎ対策として、全ノード間のつながりを可能にし、グラフ理論で分析してノードを刈り込む仕組みを入れたい。展開されないツリーは刈り込み対象と考えている。
- グラフ構造（意識して書いたもの）と、頻度・時間・書き込み/削除/再書き込みなどの行動ログ（無意識の表れ）を組み合わせて、夢・重要性・必要性・緊急性を分析したい。
- ユーザーの行動（何度も延期・復活するタスク、ツリーごとの着手の速さの偏りなど）から、何に追われ何をしたいのかを分析する機能を入れたい。
- 後でグラフ分析できるよう、データは CSV など汎用形式で、他のグラフ分析ソフトと共通性のある形式で出力する。
- 買い物は「重要性 × 必要性」の2軸で分析し、リストに挙げて買わなかったものを節約額として表示する。

### 1.3 想定ユーザー
- まず開発者本人が毎日使い、必要な機能やユーザー要望を少しずつ追加する。
- 販売時の想定ユーザー層は**未確定**（明示された記録なし）。

- 日／週／月 表示（PageUp／PageDown で前後、今日へ）。時間割は朝5時〜翌朝5時（0〜5時の予定は前日の列の下に「翌」で表示）。

- 予定をダブルクリック → タスクの設定。
- タスクをコピー（Ctrl+C）して貼り付け（Ctrl+V・右クリック）＝同じタスクの「続き」の時間枠（`sessions`）。

  - 境界線（デイリー欄とスケジュールの間）をドラッグで高さを変える。

  - 1日に複数回のタスク：設定回数を達成するたびに王冠 ♛ が1つ増え、新しいチェックボックスが出る（完了の表示にせず、位置も動かさない）。

### 3.5 タスクの設定画面（ダブルクリック・W など）
- 2列構成。左：基本（名前・種類［タスク／予定］・カテゴリ・印［🔁繰り返しタスク／Adhoc／トライアル／☆注目ノード］）、指標（重要度・必要度・緊急度を 1〜6・なし のラジオボタンで。分類＝4象限を表示）。右：いつやるか、日時、通知。
- いつやるか：1回（時刻あり）／1回（時刻なし・デイリー）／毎日／平日／毎週／毎月／反復（毎日・実施回数を表示）／複数回数実施（毎日・時刻なし、1日1〜5回）。間隔・終了日・曜日。
- 日時：日付（年・月・日の3つの箱、📅 で月のカレンダーから選ぶ。このカレンダーに**私のシフト（取り込んだ勤務）を表示**）、**開始時刻と Duration**（所要時間。「30分」「1時間30分」「1:30」「90」などで入力可。終了時刻を下に表示）、時刻なし。
- 日付と時刻の片方だけを変えたら、変えていない方は元のまま引き継ぐ。時刻だけ入れて日付が空なら、元の日（なければ選んでいる日・今日）。
- カレンダーで「続き」の時間枠を選んで開いたとき、または日時を「続き」の時間枠だけで持つタスクのときは、その回の日時を表示・編集する。
- 通知：アラーム（なし／60〜5分前）・警告音・定時アラーム。重要期限（期限日の◯日前から知らせる／常に表示／期限日だけ表示、📌 たたんでも常に表示）。
- ボタン：タスク設定を外す、📝 メモ、キャンセル、保存（Enter／Ctrl+S。閉じたり他を選んだりしたときも変更があれば自動保存）。

### 3.6 タスクリスト（右パネル）

### 3.10 IN/OUT_Navi（ツール ▸ IN/OUT_Navi。2026-11-08 に「購入分析」から改名）
- 品の**状態**：Wants（欲しい・検討中）／Buy（買う）／Hold（保留＝今は買わない）／Clutter（買わない・無駄）／Sold（売った・手放した）。以前の「購入・購入予定・今は買わない」のチェックは廃止。状態を変えた日（変更日）と、その履歴（status_log）を記録する。
- 品目の一覧（分類・状態・品名・カテゴリ・生活必要度・人生価値度・価格・**売却価格・購入−売却・売却／購入（分類）・Duration**・毎回・追加日・変更日）。リストに直接入力（売却価格もクリックして入力）、★はクリックした位置の段階に。並べ替えを3段まで重ねる。状態ごとのまとまりに小計・総計。欄が多いので横にスクロールできる。
- 上の**状態の札**（すべて・Wants・Buy・Hold・Clutter・Sold、件数つき）：押すとその状態だけを抽出表示。リストの「状態」欄（⠿）や IN/OUT_Navi マップの円を札へ**ドラッグ＆ドロップ**すると状態が変わる。状態の欄をクリック（ドラッグせずに離す）すると一覧から選べる。下の「状態を変える ▾」でも可。抽出表示中に追加した品はその状態になる。
- **Hold の上限**：カテゴリごとに Hold にしておける品の数（カテゴリの編集 ▸ Hold の上限…）。超えるときは確認し、下の欄に「衣類 4/1 ⚠超過」のように表示。
- **売却価格 ÷ 購入価格**で分類：1以上＝投資、0.5〜1＝耐久消費、0.25〜0.5＝消耗品、0.25未満＝使い捨て。
- 毎回買う品を Buy にすると、購入の記録を別の行に作り、元の品は残す（以前の購入チェックと同じ）。
- IN/OUT_Navi マップ：横＝生活必要度、縦＝人生価値度（6段階、**6＝高い、4以上が高**）。円の大きさ＝価格。印：◌ Wants、● Buy、うすい灰色 Hold、✕ Clutter、◆ Sold。4象限：トレジャー／デイリー／ロマン／箪笥の肥やし。
- **Duration**：状態ごとに、その状態にあった日数の合計（今の状態は毎日加算）。Wants → Buy にしても Wants の日数は残り、また Wants に戻るとそこから加算する（状態の履歴 status_log から計算）。リストには今の状態の Duration を表示。
- 集計（選んだ月 か すべて）：**購入金額＝Buy → Hold にした品の価格**、**売却金額＝Clutter → Sold にした品の売却価格**（その月に変えたもの。同じ品は最初の1回）。4象限ごとの購入金額、Duration（状態ごとの品数・平均・最長）、**売却価格／購入価格**（平均と4分類の件数）。下段は**1年間の推移**：月ごとの購入金額（4象限の積み上げ）と売却金額の棒。月ごとの表：購入金額・購入品数・売却金額・売却品数。
- 集計の決まり：Buy＝その期間に買った品（今 Buy か Sold）、Sold＝その期間に売った品、Wants・Clutter・Hold＝その期間にその状態にした品。リストの「追加した月」の絞り込みは追加日で行う（状態を変えても消えない）。
- 円をクリックでリストのその品へ。**Ctrl＋クリックで複数選択**（赤い輪）。
- 閉じたらすぐファイルに保存。

## 4. UI・デザインのルール（決定事項）

1. **リストへの直接入力（全画面共通・最重要）**：リストがあるものに、別の入力コンソール（追加欄）を設けて追加する方式は採用しない。基本はリストに直接入力する（いちばん下の「＋ 新しい◯◯」の行など）。
1-2. **リストの操作はエクセルと同じ（全画面共通・最重要。2026-11-08 利用者の指示）**：対象は IN/OUT_Navi・買い物リスト（PC・Android）・タスクリスト。
   - **並べ替えの決まり（4.1 で変更）**：行に入力している途中は並べ替えない（行はその場に残る）。次のときに並べ替える：①Enter・Tab でその行のデータの欄を最後まで進んだ（入力を終えた）、②ほかの行・ほかの物（マップ・カレンダーのノードなど）を選んだ、③画面を切り替えた（一覧の外へ移った・表示を変えた・別のタブ）。「⇅ 並べ替える」ボタンでもすぐ並べ替える。新しく追加した品は、入力を終えると「＋ 新しい◯◯」の行へ戻る（続けて追加できる）。
     - データの欄（Enter・Tab で回る順）：IN/OUT_Navi＝品名→カテゴリ→状態→生活必要度→人生価値度→価格→売却価格、買い物リスト＝品名→個数→価格→必要度、タスクリスト＝タスク→重→必→緊。Android の買い物リストは、キーボードの「次へ」で同じ行の次の欄、価格の「完了」で入力を終える。
     - 以前（4.0 まで）は「⇅ 並べ替える」を押したときだけ並べ替えていた。
     - 並べ替えを待つのは**リストの並びだけ**。分析マップ・マップ・カレンダーなどリスト以外は、データが変わったらすぐに反映する（これまでどおり。利用者の確認）。
   - セルを1回クリックで選ぶ（太い青の枠）。**文字を打つとそのセルに入力**（今の中身を置きかえる）、F2・ダブルクリックは今の文字のまま入力。Enter・Tab＝次のデータの欄へ（Shift+Tab で前へ）、↑↓＝上下の行、←→＝隣の欄（入力中は文字の端で隣へ）、Esc＝取り消し。
   - 文字以外の欄：☐ はスペース・クリック、★ や 重・必・緊 は 1〜6 のキー、必要度（買い物リスト）は 1・2・3、状態（IN/OUT_Navi）は W・B・H・C・S のキー、一覧から選ぶ欄（カテゴリ・状態・必要度・分類・日時・📝）はスペースで開く（Enter は次の欄へ）。
   - 仕組み：`GridNav`（mind_navi.py）。いちばん下の「＋ 新しい◯◯」の行は、クリックか Enter・文字を打つとすぐ入力。
2. **入力中に文字を大きくしない（全画面共通・最重要）**：リストやテキストボックスへの直接入力中に文字が大きくなる UI は禁止（「レスポンスが遅くなる・見づらい・最悪の UI」との指摘。以降も徹底）。入力欄は表示中の文字と同じ大きさ・同じ書体で、セルと同じ大きさに重ねる。Windows の日本語入力（IME）の変換中の文字も入力欄と同じ書体・大きさにする処理を入れた（`install_ime_font_fix`。実機未確認 → 9章）。
3. **4象限の色（カレンダー・タスクリスト・スケジュール［ガント］で共通）**：Core＝赤（#e03131）、Operational＝紫（#7048e8。2026-11-08 に青 #1c7ed6 から変更）、Strategic＝緑（#2f9e44）、Divest＝灰色（#868e96）、Adhoc＝黄色（#f5b800、地の色 #fff3bf）。
4. **緊急度の表し方**：地の色ではなく縁取り（左右の縦線）。緊急度が高いほど縦線が濃く太い。以前のマゼンタの枠と「急」の札は廃止。
5-1. **アルファベット1文字の札は使わない（4.1〜4.2、利用者の指示）**：カテゴリ・分類・状態を表す頭文字の札（カレンダーの C・O・S・D、IN/OUT_Navi の W・B・H・C・S、Google 同期の G）は廃止し、色分けで表す。印は、見て意味が分かる絵の記号だけにする（📝 メモ・📌 常に表示・🔁 繰り返し・♛ 王冠・↻ 定期・⧉ 続き・☆ 注目・⚠ 期限切れ・🛒・📊・☁ 同期済み などは使ってよい。利用者の確認）。
5-2. **完了したタスクは隠さない（4.2、利用者の指示）**：マップの完了チェックとカレンダーの完了チェックは同じもの（同じタスクの完了）。完了してもマップ・カレンダーとも消さず、目立たない表示（灰色の文字・うすい地）にするだけ。
5. **4象限の表記**：Core／Operational／Strategic／Divest と英語。2行で出す所は2行目が日本語（最優先／効率化・委任／計画的投資／削減）。タスクリストの分類欄は略称 Core／Ops／Strat／Divest。カレンダーの頭文字の札（C／O／S／D）は 4.1 で廃止（色で表す）。
6. **評価の段階（タスク）**：重要度・必要度・緊急度はそれぞれ6段階で、**小さいほど重い（1位・2位という順位のイメージ）。1〜3 を「高」**。4象限は 重要度高×必要度高＝Core、重要度低×必要度高＝Operational、重要度高×必要度低＝Strategic、重要度低×必要度低＝Divest。タスク分析マップの軸もこれに合わせて反転（1位が右・上）。
7. **評価の段階（IN/OUT_Navi＝旧 購入分析）**：生活必要度・人生価値度は6段階で **6＝高い、4以上が高**（コードから確認）。タスクの指標と向きが逆。統一するかどうかは未確定（9章）。
8. **買い物リストの必要度**：高・中・低（1・2・3）。既定は中。クリックで一覧から選ぶ。
9. **用語**：「アドホック」→「Adhoc」。「設定タスク」→「タスクリスト」。「今回の買い物」→「買い物リスト」。
10. **表示デザインの切り替え（配色）**：オフィス（標準）／ハッカー（攻殻機動隊のような黒と緑）／深海／仏教（タイ初期仏教）。ツールバーの「デザイン」または 表示 ▸ デザインスタイル。4象限の色の決まりはそのまま。Vipassana の画面は独自の配色のまま。
   - 仕組み：tk の色指定を置き換える（`_theme_map_factory`）。オフィスのときは置き換えを入れない（描画を遅くしないため）。色を指定していないキャンバスの文字は #212529 として扱い、配色に合わせる。
   - 深海・ハッカーは「見づらい」との指摘が2回あり、そのつど文字を明るく・地を暗くして改善した（最終確認は利用者側で未了）。
11. **表示スタイル（レイアウト）**：オフィス／ノート／マインドマップ／カレンダー／ガント（Ctrl+1〜5）。
12. **アクションはクリック＋ショートカット**：アイコンボタンではなく、ノードのクリックでサブタスクを追加でき、クリック操作にはショートカットキーも付ける（初期の方針。メモリーから）。
13. **複数のマップは上部の5つのボタンに登録して切り替え**。
14. **選択したタスクの強調**：カレンダーで選ぶと他の画面の同じタスクを3回点滅 → 目立つ表示。

### 5.2 バックアップの仕組み
1. **同じフォルダのバックアップファイル（全く同じ内容）**：保存のたびに `<名前>.backup.json` を同じフォルダに書く（例 `mind_navi.json` → `mind_navi.backup.json`）。データファイルが壊れて開けないとき、これを最初の候補として復元を確認する。Android版はこのファイルを書けない（選んだファイルにしか書けないため）。スマホでの変更は、次に PC版が保存したときに反映される。
2. **この PC の自動バックアップ（ローカル）**：`~/.mind_navi_backups/`。未保存の変更を1分ごとに保存（無題のマップはボタン番号ごと）。画面を切り替えるたびの版（`versions/`、ファイルごとに最新30版）。元に戻す履歴（`undo.json.gz`、30操作）。開くときに保存ファイルより新しいバックアップがあれば、どちらから開くか確認。
3. **バックアップ（復元ポイント。4.5 で決めなおし、2026-11-08 利用者の決定）**：`rp_write`・`rp_periodic`・`rp_on_open`。
   - 置き場所：**データフォルダ（Google ドライブ）の `Mind_Navi_backups/<名前>/`**。同じものを**この PC（`~/.mind_navi_backups/points/`）にも写しとして**置く（フォルダごと消えたときの備え。データを分けるのではない）。gzip で圧縮。
   - 種類と残す数（種類ごとに新しいものから）：5分ごと・30分ごと・1時間ごと・1日ごと・2日ごと・3日ごと・1週間ごと・1か月ごと・3か月ごと・1年ごと は**2つずつ**（1つ前は必ず1〜2期間前の中身になり、気づくのが遅れても抜ける期間が出ない）。開いたとき（読み替える前の中身そのまま）・閉じたとき（最後に保存した後の中身）は**10回分**。**バージョンアップの前**（前の版のソフトで保存したファイルを新しい版で開いたとき、何かを書く前の中身。`view.mn_guard.ver` で判定）は**消さない**。ほかに 保存前の退避 30・戻す前 20。
   - ファイル名：`<種類>_<日時>_<PC の名前>_<中身の指紋>[_v<元の版>].json.gz`。**PC ごとに分けて数える**（家と学校の PC が互いのバックアップを押し出さない）。
   - **中身が前と同じなら書かない**（使っていない間に、同じ中身で古いバックアップを押し出さない）。
   - 書いたら読み直して確かめ、確かめられたときだけ古いものを消す。
   - 時間ごとの種類は、保存したときと開いたときに「その種類を最後に書いてから期間が過ぎたか」で書く（PC を閉じていた間の分は、次に開いたときに書く）。スマホで変えた分は、PC で開いて保存したときに入る（スマホは別のファイルを書けないため）。
   - 4.4 までの種類（1時間ごと 48・毎日 120・毎月 36 など、名前に PC が入っていないもの）は消さず、一覧に出して戻せる。
4. **保存前の安全確認（2026-11-08）**：`_save_guard`。保存しようとしているデータが、前に保存したときより半分以下に減ったら（ノード・IN/OUT_Navi の品・IN/OUT_Navi の入力のある品・買い物リストの品）、今のファイルの中身を「保存前の退避」として残す。ノードが減ったとき・IN/OUT_Navi の品はあるのに入力だけ消えたときは、画面でも知らせる。
5. **「ファイル ▸ 復元ポイント（バックアップ）から戻す…」**：復元ポイント・自動保存の版・同じフォルダの .backup・以前のPCの購入分析（`~/.taskmap_shopping.json(.imported)`）から選び、**全部／IN/OUT_Navi だけ／買い物リストだけ**を戻す、または **IN/OUT_Navi の消えた入力を補う**（同じ id の品で、今は入力が消えているものだけ。`shopping_fill_lost`）。選ぶと中身の数（ノード・IN/OUT_Navi の品と入力のある品・買い物リストの品）を表示。Google ドライブの「版を管理」でダウンロードした古いファイルも［ファイルを選ぶ…］で使える。戻す前の中身は「戻す前」に残る。
6. IN/OUT_Navi を開いたとき、3品以上あってすべての品の入力（状態・★・売却価格・履歴）が無ければ、復旧をすすめる。
7. **3方向でまとめる保存（4.4）**：`merge3`・`_merge_outside`・`_apply_doc`。開いたとき・保存したときの中身を `_base_doc` に覚えておき、保存の直前にファイルが外で変わっていたら（ほかの PC・スマホ）、**前の中身・この PC・ファイルの3つを比べて両方の変更を残す**（辞書は項目ごと、id のある品のリストは品ごと。片方だけが変えた所はその変更、両方が同じ所を違う値に変えたときだけこの PC の値。片方で消した品をもう片方で変えていたら残す）。まとめた結果を画面にも反映する。ほかの PC の変更は、ウインドウに戻ったとき・20秒ごと・自動保存のときに同じ方法で取り込む（入力中は待つ）。4.3 の「保存の前の守り（減る保存は前の中身から戻す）」は場当たりの対策なので廃止した。
   - **【4.8】ほかの側に無いことは「消した」とみなさない（足した方が勝つ）**：`merge_doc`。4.4〜4.7 は、ファイルに無い項目を「ほかの PC で消した」とみなしていた。さらに「この PC で何も変えていなければファイルの中身をそのまま使う」近道があった。そのため、Google ドライブの同期が遅れた PC・古い版の PC・スマホが古い中身でファイルを書くと、20秒ごとの取り込みでその古い中身をそのまま受け入れ、次の保存で全ての PC からウィークリーコンパス・デイリーコンパス・振り返り・デイリータスクの実施の記録が消えていた（利用者の報告。再現して確認）。4.8 では、消したとみなすのは次の3つだけにした：この PC で消したとき、ゴミ箱に入れた記録（`trash_tombstones`）がある id、スマホが書く買い物リストとつながり（親の付けかえ）。ほかの PC で外した実施の記録などは、この PC に残っていれば戻ってくることがある（消えるより安全なので、こちらを選んだ）。
   - **すべてのバックアップから集めて戻す（4.8）**：`fill_doc`・`recover_all`。［ファイル ▸ すべてのバックアップから、消えたものを集めて戻す…］・［復元ポイントから戻す］の画面のボタン。この PC とデータフォルダの復元ポイント・自動保存の版・.backup を新しい順にすべて調べ、今は消えている・空になっているものだけを足す（今の入力は変えない。ゴミ箱に入れたものは戻さない）。4.8 で初めて開いたときに1回だけ聞く。
10. **ゴミ箱（4.4）**：`view.trash`（`trash_add`・`trash_restore`。最大3000件、データファイルに入る）。ノードの削除（下位とつながりも）・タスクの設定を外す（予定・実施の記録・繰り返し）・IN/OUT_Navi の品・買い物リストの品と定番を消すと、消す前の中身が入る。［ファイル ▸ ゴミ箱（消した・外したものを戻す）…］で選んで戻す（今あるものは変えず、無いもの・空になった項目だけ足す）。
11. **復元は足すだけ（4.4）**：［復元ポイントから戻す］は「この時点から、消えたものを戻す」（`fill_missing`：消えたノード・つながり・品・振り返り・項目だけを足し、今の入力は変えない）と「IN/OUT_Navi の消えた入力を補う」だけ。丸ごと置きかえる戻し方は廃止（4.0 の「全部／IN/OUT_Navi だけ／買い物リストだけ を戻す」は、戻した時点より後の入力を消していた）。
12. **使用中の札（4.7・5.1）**：`inuse_write`・`inuse_others`・`inuse_unseen`。データフォルダの `Mind_Navi_backups/<名前>/inuse_<PC の名前>.json` に、開いている PC の名前・時刻・**最後に保存した中身の指紋と時刻**を置く（5分ごとに書き直し、閉じたら「閉じた」にする。データではない）。
    - 開いたときにほかの PC の新しい札（15分以内・閉じていない）があれば**知らせるだけ**で、ふつうに開いて保存する（5.1）。4.7〜5.0 の「見るだけで開く」は、入力できるのに保存しなかったため、家で開いたまま職場で開いて「はい」を選ぶと、職場で入力したものがすべて消えた（利用者の報告。再現して確認）。廃止。
    - **同期の待ち（5.1）**：ほかの PC が10分以内に保存した中身（札の指紋）が、まだこの PC のファイルに届いていない（Google ドライブの同期待ち）ときは、上書きしないよう保存を待つ（15秒ごとに見直す。届いたら両方をまとめて保存）。閉じるときは最長60秒待ってから保存する。排他ロックは Google ドライブではほかの PC に伝わらないので使わない。
8. **開いたときの確認（4.3）**：保存のたびにデータの数（ノード・IN/OUT_Navi の品と入力・買い物リスト）と版を `view.mn_guard` に書く。開いたときに今の数がその半分未満なら（古い版の Mind_Navi のPCなどで上書きされたとき）、知らせて復元ポイントの画面を開く（その数がいちばん多い時点を選んでおく）。
9. 題名の欄に版番号を出す（どの版で動いているか分かるように）。

### 5.3 Google ドライブでの共有
- 方針（決定）：Google ドライブの中にフォルダを作り、その中にすべてのデータファイルを保存する。データは基本1つのファイル。処理が重くなり分割したほうがよい場合も、Google ドライブのそのフォルダの中に保存する。
- PC版：［ファイル］→［データの保存フォルダ（Googleドライブ）…］で、マイドライブの中の `Mind_Navi` フォルダを作る／選ぶ（Windows の G:\マイドライブ 等、~/Google Drive/My Drive、Mac の ~/Library/CloudStorage/GoogleDrive-*/My Drive を自動で探す）。設定すると、上の1〜5に登録したファイルをそのフォルダへコピーして切り替える（元のファイルは残す）。同じ名前のファイルがすでにフォルダにあれば「そちらを使う／別名でコピー／移さない」を確認。
- 保存フォルダの外のファイルを開いているときは、タイトルバーに「⚠ Googleドライブのデータフォルダの外に保存中」。
- **データはすべてデータフォルダの1つのファイルに入れる。一部のデータだけ別のファイルを裏で作らない**（絶対の原則。2026-11-08 利用者の指示）。アラーム・重要期限・振り返りの知らせを出した記録も、4.5 からデータファイルの `view.remind_state`（以前の `~/.mind_navi_reminders.json` は1回だけ取り込み、`.imported` に名前を変える）。Google のログイン情報は鍵のようなものなので PC の中のまま。
- **PC ごとの設定はローカル**（共有しない。データではない）：`~/.mind_navi_slots.json`（ボタン1〜5の登録・データフォルダ・マウスのボタン・デザイン・左右パネルの幅など）、`~/.mind_navi_viewstate.json`（終了時の表示）、`~/.mind_navi_google.json`／`_token.json`（Google の設定・認証）、`~/.mind_navi_tide_cache.json`、`~/.mind_navi_sounds_v2/`・`~/.mind_navi_bell_soft.wav`（Vipassana の音）、`~/.mind_navi.lock`（二重起動防止）、`~/.mind_navi_backups/`（5.2）。
- 以前このPCだけに保存していたファイル（`~/.taskmap_shopping.json`、`~/.taskmap_memo.json`、`~/.taskmap_lectures.json`、`~/.taskmap_shift.json`）は、起動時にデータファイルへ取り込み（足し合わせ。同じ id は足さない）、`.imported` に名前を変える。`~/.mind_navi_categories.json`（起動時に旧 `~/.taskmap_categories.json` からコピー）は旧データで読むだけ。

### 5.4 PC版と Android版の互換ルール
1. ファイルは分けない。Android版は**同じデータファイルの `view.groceries` だけ**を書き換え、それ以外は読んだとおりに書き戻す（キーの順番・数の書き方 0.0 なども変えない）。
2. Android版は保存の直前にファイルを読み直し、`view.groceries` だけを差し替えて書く（PC で変えた他の部分を消さない）。
3. PC版は、開いた後にファイルが外で書き換えられたとき（スマホ・ほかの PC）、3方向でまとめて取り込む（5.2 の7。4.4 から。以前は買い物リスト以外も変わっていたら自動保存を止めて警告し、そのあと保存すると、ほかの PC の変更を上書きして消していた）。確認のタイミング：ウインドウに戻ったとき・20秒ごと・買い物リストを開いたとき・自動保存のとき。
4. 画面の欄（並び・見出し）は PC版と同じ。`view.groceries.layout` を PC版が書き、Android版が読む。
5. **開発方針（決定）**：PC版の買い物リストの仕様を変えたら、Android版も合わせてバージョンアップする。Android のインストールファイルは前の版を確認し、versionCode を上げて同じ署名で作る（上書き更新できるように）。
6. データファイルを別のフォルダへ移したら、Android版で「ファイル」から選び直す。

## 6. 決定事項とその理由

「変更前 → 変更後（理由）」の形。理由が記録に残っていないものは「理由の記録なし」と書いた。

### 6.1 全体・開発の方針
- PC版は **1ファイル（mind_navi.py）** で納品する（利用者の希望）。標準ライブラリ（tkinter）だけで動き、追加ライブラリは任意の機能だけで使う。
- 開発環境：チャット → **GitHub（プライベートリポジトリ）＋ Claude**（自宅・学校など複数の PC から開発指示を出したいため）。
- 作業の報告には毎回、取り込み〜ダウンロード〜入れ替えの手順まで書く（2026-11-08、利用者の指示。手順は CLAUDE.md）。
- 版番号：上げるかどうか毎回確認 → **指示ごとに上げてよい**（PC版は小数点以下を1つ。2026-11-08、利用者の了承）。プルリクエストも確認なしで作ってよい（取り込みは利用者）。
- 名称：TaskMap → **Mind_Navi**（2026-11-08、利用者の決定。内部の名前まで変更。冒頭の注記を参照）。
- 最終的に Windows のインストールファイルを作る（方式は未確定）。
- PC版の買い物リストを変えたら Android版も合わせてバージョンアップし、Android の画面構成（欄）は PC版と同じにする（データの互換を保つため）。
- データはすべて1つのファイル、そのファイルと**まったく同じ内容のバックアップファイル**をもう1つ保存（壊れたとき用）。
- データの保存場所：各 PC のローカル → **Google ドライブの中のフォルダ**（「データをローカルに保存して他の PC から見られない」ことが頻発したため）。分割が必要な場合も同じフォルダの中に置く。
- **データは財産。消さない・壊さない**（2026-11-08。3.8 の不具合で IN/OUT_Navi の状態・★などが消えた。利用者の指示で再発防止を入れた）：
  - 原因：IN/OUT_Navi のデータを読み替える処理が、形式 4 を「最初の形式」と取り違えて品を作り直していた。もう1つ、買い物リストを開くたびに個数を1に戻していた。
  - 対策：読み替えは関数（`shopping_upgrade`・`groceries_normalize`）にし、**作り直さず足りない項目を足すだけ・何度呼んでも同じ・知らない項目は消さない**。自動テストで確かめる。復元ポイント（開いたとき・1時間ごと・毎日・毎月、このPCとデータフォルダの両方）、保存前の安全確認、復元ポイントから戻す画面（5.2）。
- **勝手に消さない（4.4、2026-11-08）**：IN/OUT_Navi・振り返りノート・カレンダーの実施済みのタスクが消えた（利用者の報告）。利用者の指示「数が減ったら前の版から戻すような場当たりでなく、勝手にデータを消さない根源的な対応を」で原因を調べ、次のとおり直した。
  | 原因 | 何が消えたか | 4.4 の対応 |
  |---|---|---|
  | 複数の PC で同じファイルを開いたまま使うと、古い中身を持つ PC が保存したときに、ほかの PC の入力を上書きしていた（警告は出していたが、閉じるときの保存・Ctrl+S では上書きした） | 振り返りノート・IN/OUT_Navi・完了など、ほかの PC で入力したもの全部 | 保存は3方向でまとめる（5.2 の7）。ほかの PC の変更は定期的に取り込む |
  | 復元ポイントから「全部／IN/OUT_Navi だけ」戻すと、その時点より後の入力を丸ごと置きかえていた（4.0） | 戻した時点より後の入力 | 復元は足すだけ（5.2 の11） |
  | タスクリストで Delete・BackSpace を押すと、タスクの設定を外していた（予定・実施の記録・繰り返しを消す）。エクセルと同じ操作にしたので押しやすくなっていた | カレンダーの予定・実施済みのタスク | Delete・BackSpace はセルの中身を消して入力するだけ |
  | 「リストから外す」「完了済みを外す」・マップの F キーが、タスクの設定ごと外していた | カレンダーの予定・実施済みのタスク | タスクリストに出さないだけにした |
  | IN/OUT_Navi・買い物リストの Delete で、確認なしに品を消し、次の行へ移るので押し続けると次々に消えた | IN/OUT_Navi・買い物リストの品 | Delete では消さない。✕・右クリックで消した品はゴミ箱へ |
  | Ctrl+Z がどこでもマップ全体を前の状態に戻していた（文字を入力中でも） | 直前に入力したもの | 入力欄では効かせない |
  | **（4.6 で発見）マップで新しいノードを作って名前を入れずに Esc（または空のまま確定）すると、取り消しの処理がマップ全体を「元に戻す」の記録で置きかえていた。この記録には振り返りノート・IN/OUT_Navi・買い物リスト・メモなどを入れていないので、次の保存でそれらが全部消えた**（ずっと前の版から） | 振り返りノート・IN/OUT_Navi・買い物リスト・メモ・ミッション・知らせの記録 | 取り消しは作ったノードだけを消す。元に戻す（Ctrl+Z）でもデイリーコンパス・ゴミ箱を前に戻さない（`UNDO_KEEP_VIEW`）。保存のとき、別画面のデータの欄そのものは丸ごと無くならない（前に読んだ中身から残す） |
  | **（4.8 で発見）保存のときのまとめ（4.4〜4.7）が、ほかの側に無い項目を「消した」とみなし、何も変えていない PC はファイルの中身をそのまま使っていた。同期の遅れた PC・古い版の PC・スマホが古い中身を書くと、全ての PC でその古い中身が広がった** | ウィークリーコンパス・デイリーコンパス・振り返り・デイリータスクの実施の記録 | ほかの側に無いことは消したとみなさない（足した方が勝つ）。わざと消したものはゴミ箱の記録で見分ける。すべてのバックアップから集めて戻す |
  | **（5.1 で発見）家で開いたまま職場で開くと「ほかの PC で開いたまま」と聞き、「はい（見るだけで開く）」を選ぶと、職場で入力できるのに保存しなかった（4.7〜5.0）** | 職場で入力したもの全部 | 知らせるだけにして、ふつうに保存する。ほかの PC の保存が同期で届いていなければ、届くまで保存を待つ |
  | 3.8 の読み替えの不具合（形式4を最初の形式と取り違えた）・買い物リストの個数を1に戻す（4.0 で修正済み） | IN/OUT_Navi の入力・個数 | 読み替えは足すだけ（4.0） |
  - 決まり：消す・外す操作はすべてゴミ箱に入れる。キー1つで行・品・タスクを消さない。中身のあるものを消すときは確認する。復元は足すだけ。保存で他の変更を上書きしない。
  - 古い版の PC が保存すると、その PC では3方向でまとめないので、また上書きが起こる。**すべての PC を 4.4 以上にする**。
- **速さを第一に優先する**（2026-11-08、利用者の指示）。そのための決定：
  - マップは画面に入るノード（と画面を通る線の両端）だけを描く。画面の外のノードは前に描いたときの大きさで位置だけ見積もる（全体図・全体表示に使う）。整列のための計測では全部描く。
  - バックアップ（`.mind_navi_backups`）・版・元に戻す履歴の書き込みは別の処理（`BgWriter`）で行い、画面を待たせない。データファイル本体と同じフォルダの `.backup.json` は今までどおりその場で書く。終了時・ファイルを開くときは書き終わるのを待つ。
  - 元に戻す履歴は速い圧縮で、変わっていないときは書かない（以前は保存のたびに最大30版を最大圧縮し直し、1秒ほど止まっていた）。
  - 週間実績の日ごとの集計はまとめて数え、文字幅の計測は文字列ごとに覚える。画面の大きさの変更による描き直しは1回にまとめる。
- 購入分析・メモ・講義・勤務の設定：各 PC のファイル（`~/.mind_navi_*.json`）→ データファイルの中（`view`）へ（他の PC で購入分析が見られなかったため）。アラーム・振り返りの知らせを出した記録も 4.5 でデータファイルへ（「データはすべて1つのファイル」の原則）。
- バックアップ：開いたとき・1時間ごと・毎日・毎月 → **12種類**（5分・30分・1時間・開閉・1日・2日・3日・1週間・1か月・3か月・1年・バージョンアップの前。4.5、利用者の決定）。各種類を1つだけにすると、消えたことに気づくのが遅れたときに戻せない期間が出るので2つずつ。複数の PC が同じフォルダに書くので PC ごとに分ける。中身が同じなら書かない（5.2 の3）。
- こまめな自動保存：操作のたびに少し後で保存＋30秒ごと（入力・ドラッグ中、**文字を打っている間〔最後のキーから1.5秒〕**は避ける）、買い物リスト・購入分析・メモを閉じたらすぐ保存（「操作系に負担の出ない範囲で」という条件つき）。

### 6.3 タスク・指標
- 優先度（1〜3）→ **廃止**。
- 指標：重要度と必要度（と緊急度）を **6段階** で入力。入力：ドロップダウン → ラジオボタン（ドロップダウンに気づかれず「未実装」と言われたため）。
- 指標の向き：大きいほど高い（6が高い）→ **小さいほど重い（順位のイメージ。1〜3が高）**。既存データは 7−v で読み替え（`view.idx_rank_v1`）。タスク分析マップの軸も反転。
- 重要期限の表示：日時 → **残り日数**（50年先まで）。📌 で、たたんでも常に表示 → さらに**スクロールしても常に上に表示**。
- 延期の判定（最新）：「終了時刻がまだ来ていない（今より後）タスクを動かしたとき、開始時刻が今をまたいで今以降になったら延期」。それ以外の移動は延期にしない（以前の判定の詳細は記録に残っていない）。
- タスク設定画面の時刻：開始〜終了 → **開始＋Duration**。日付・時刻の片方だけ変えたら、もう片方は元のまま引き継ぐ。
- 週間実績・振り返りのタスク分類別：Adhoc を4象限と別に「Adhoc」として集計。

- Python：Claude 側のテストは **Python 3.12**（Linux＋xvfb）。構文上 3.8 以上が必要（`:=` を使用）。最低動作版は未確認。
- 必須：標準ライブラリのみ（tkinter を含む Python。Windows の公式インストーラーなら tkinter は入っている）。
- 任意（その機能を使うときだけ）：

| 機能 | ライブラリ | 入れ方 |
|---|---|---|
| 分析用の変換（networkx） | networkx | `pip install networkx` |

## 11. Android版のビルド方法

### 11.1 プロジェクト
- 場所：`android/MindNaviShopping/`（Java のみ、外部ライブラリなし）。パッケージ `jp.mindnavi.shopping`、minSdk 26（Android 8.0）、targetSdk 34、compileSdk 34（Gradle 用の設定）。
- ファイル：`app/src/main/java/jp/mindnavi/shopping/MainActivity.java`（画面・読み書き）、`Json.java`（JSON を書き方を変えずに読み書き：キーの順番を保つ、数は読んだときの文字のまま）、`AndroidManifest.xml`、`res/values/strings.xml`、`res/mipmap-*/ic_launcher.png`（アイコン）、Gradle の設定（`settings.gradle`、`build.gradle`、`app/build.gradle`、`gradle.properties`、`gradlew`・`gradle/wrapper/`）、`tools/build_apk.sh`、`README.md`、署名の鍵 `signing/`（11.4）。
- Google ドライブのファイルは Storage Access Framework（ACTION_OPEN_DOCUMENT と永続的な権限）で読み書きする。

### 11.2 APK の作り方（実際に使った方法：Gradle を使わない）
Ubuntu 24.04 で確認：
```
sudo apt-get install -y aapt android-sdk-platform-23 apksigner dalvik-exchange zipalign openjdk-21-jdk-headless
cd android/MindNaviShopping
export MIND_NAVI_KEYSTORE=/path/to/mind_navi.keystore MIND_NAVI_KS_PASS=（パスワード）
bash tools/build_apk.sh          # 出力：/tmp/mind_navi_apkbuild/MindNaviShopping_v<versionName>.apk
```
- 手順の中身：aapt でリソース → javac（`--release 8`、android.jar は API 23）→ dx（`--min-sdk-version=26`）→ aapt で APK → zipalign → apksigner（v2・v3 署名）。
- versionCode／versionName は `app/build.gradle` から読む。**更新するときは versionCode を必ず1つ上げる**（前の版の上から上書きインストールできるように）。
- 注意：ソースでラムダ式・メソッド参照を使わない（dx が変換できず Android で動かない。スクリプトが検出して止める）。API 24 以降の機能（List.sort、java.time など）は Android 8.0 以上の実機の実装を使う前提。
- AndroidManifest.xml には package と uses-sdk が無い（Gradle 用の書き方）。スクリプトがビルド時に足す。

### 11.3 Android Studio（Gradle）で作る方法（未確認）
- フォルダを Android Studio で開き、Build ▸ Build APK(s)。AGP 8.5.2、Gradle 8.7（wrapper）、JDK 17。
- この方法はネットワークの制限で一度も確認できていない。また署名の設定（signingConfig）が無いため、配布中の APK と署名が違うものになる。

### 11.4 署名
- 鍵：`android/MindNaviShopping/signing/mind_navi.keystore`（PKCS12、別名 `taskmap`、RSA 2048、有効期間 20000日）。パスワードは同じフォルダの `password.txt`。
- 経緯：2026-11-07 の移行時は「鍵とパスワードはリポジトリに入れない（利用者が保管）」と決めた。2026-11-08、利用者が元の鍵を GitHub に登録する手順が難しいため、**新しい鍵を作ってリポジトリ（非公開）に保管**することにした（利用者の決定）。
- 影響：元の鍵で署名した版（1.0〜1.2）には上書きできない。新しい鍵の版を入れるときは、一度アンインストールして入れ直し、データファイルを選び直す（買い物データは Google ドライブのデータファイルにあるので消えない）。以後は同じ鍵で上書き更新できる。
- 注意：リポジトリに入れる人は鍵を使えるので、共同作業者を加えるときは注意する。**鍵を作り直したり消したりしない**（上書き更新できなくなる）。
- 手元でビルドするときは 11.2 の環境変数に `signing/` の鍵とパスワードを渡す。

### 11.5 インストール
- APK をスマホで開き、「提供元不明のアプリ」を許可してインストール。Play プロテクトの警告が出たら「インストールする」。

### 11.6 配布ファイルの作成とダウンロード（GitHub Releases）
- `.github/workflows/release.yml`（名前「配布ファイルを作る」）。**main に取り込むと、PC版・Android版のプログラムが変わっていれば自動で作る**（2026-11-08。3.8 を取り込んだのに作り直しておらず、利用者が古い 3.7 をダウンロードしてしまったため）。手で作るときは GitHub の「Actions」→「配布ファイルを作る」→「Run workflow」で、自動テスト → 署名付き APK の作成 → Releases ページへの掲載を行う。
- 置くファイル：`mind_navi.py`（PC版。Windows・Mac 共通）と `MindNaviShopping_v<versionName>.apk`（Android版）。
- 版の名前（タグ）は `pc<PC版のVERSION>-android<versionName>`（例 `pc3.6-android1.2`）。同じ版でもう一度作ると、ファイルを差し替える。いつもいちばん新しく作ったものを「Latest」にする。
- ダウンロード：リポジトリのページ右側の「Releases」→ 版を開き「Assets」のファイルを押す。
- 署名は `signing/` の鍵を使う（11.4）。事前の登録は要らない。
- 「Run workflow」のボタンは、ワークフローのファイルが main ブランチにあるときだけ表示される。
